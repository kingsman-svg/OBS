# 弱网与RTMP低延迟优化计划

状态：2026-10-16，用户暂定范围；[第015步](015-publish-control.md)已完成队列/IO/编码统计和运行时手动码率入口。自动控制、按时间淘汰与新的低延迟策略仍待后续实现。已有基础包括有界媒体队列、NVENC低延迟配置/无B帧、直播短探测、超时取消、播放器过期画面跳过。

## 本阶段范围

| 策略 | 目标 | 首期方向 |
| --- | --- | --- |
| 发送队列优化 | 避免网络写出变慢后积压历史画面 | 同时观察队列数量与媒体时间跨度，处理过期原始帧并保持音画时间关系 |
| 自适应码率 | 发送负载随网络承载能力变化 | 基于发送耗时、队列积压和实际输出趋势调整目标码率，拥塞时较快降低，稳定恢复后缓慢提高 |
| 用户可调节码率 | 用户能控制画质与带宽使用 | 提供手动目标与自适应控制边界，显示设定值、当前目标与实际输出统计 |
| RTMP低延迟 | 降低首屏与持续播放延迟 | 测量各段延迟后调整编码/封装、传输与播放缓冲，保留稳定播放所需余量 |

本步在Windows OBS现有RTMP链路内推进。Mac上的SRS、MediaMTX、OpenH264研究项目保持独立；WebRTC拥塞控制、重传与ICE不纳入本阶段。首期先调整视频码率，音频、协议开销和关键帧峰值需要预留余量；分辨率/帧率自适应另行按需要设计。

## 建议的初版控制关系

- 手动模式：用户设置固定视频目标码率，自适应策略不覆盖它；队列有界与超时处理仍然有效。
- 自适应模式：用户设置允许的码率范围，上限体现画质/带宽偏好；策略在范围内调整。具体默认值及阈值根据基线和限带宽测试确定。
- 切换模式和修改数值都通过同一个参数提交入口，由编码线程应用；GUI不跨线程直接修改AVCodecContext。
- 编码器CBR是围绕目标分配数据；网络自适应负责改变这个目标。实际输出还受画面复杂度和统计窗口影响，界面应分别显示。
- 先验证现有FFmpeg7.1/NVENC封装能否在同一会话动态生效，再接自动策略；调整失败要如实反馈，不能只改界面数值。

以上控制关系是本计划的初版设计建议，用户暂定的四项范围不等于已确定所有界面和算法参数。

## 队列与线程边界

`MediaPublisher`当前同一工作线程负责等待媒体、编码、封装及网络写出；已有的是待编码/发送的原始视频和PCM队列，并没有单独的编码包发送线程。本步先在这一结构内增加观测和积压控制，按实际瓶颈再判断是否需要拆分。

过期视频优先在编码前处理，不任意丢弃依赖参考帧的压缩包。已经交给TCP的数据无法通过清空应用队列撤回。音频缺口、时间线跳变及恢复时的关键帧必须成套处理，避免通过补送大量历史音频重新制造积压。具体恢复策略随行为测试确定。

Publisher的写出/队列统计主要反映上行及本地处理压力，不等同于观众下行带宽；编码或GPU处理慢也可能造成积压。首期策略应避免把单一指标直接当作精确带宽估计。观众侧反馈按验收需要补充。

## 增量实施顺序

1. 记录基线：发送耗时、队列深度/媒体跨度、实际输出码率、首屏和采集到显示延迟；统计保持低开销。
2. 接入用户可调码率，先验证运行中实际码流变化、错误返回和启停线程安全。
3. 优化直播队列及RTMP编码/传输/播放缓冲，检查音画同步、正常停止与过期数据恢复。
4. 在已有参数入口上增加自适应策略、调整冷却与回升机制，再验证手动/自动切换。
5. 在隔离测试链路模拟限带宽、延迟、丢包、断网与恢复，完成持续运行验收，再推进Agent。

每个实现步骤继续维护中文成员/编号流程注释与时序图，不新增类图。每步构建验证后独立提交；本计划不预先创建新工作线程或空模块。

## 验收依据

- 带宽降低时目标码率按策略下降，恢复后回升稳定，手动模式不被自动覆盖。
- 发送/播放缓存保持有界，持续拥塞不会让延迟无界增长；恢复后可重新到达正常直播位置。
- 同时记录画质变化、音频连续性、音画偏差、卡顿比例和断网恢复耗时，避免只观察平均码率。
- 延迟用可核对的帧标记/时间基测量；跨设备不能直接相减未同步的本机时钟。
- RTMP缓冲参数、队列容量都不等于实测端到端延迟；目标数值在基线测量后确定，不提前承诺。
- 默认行为测试不影响外部网络；弱网注入只作用于明确的测试链路，并恢复测试前服务/网络状态。
