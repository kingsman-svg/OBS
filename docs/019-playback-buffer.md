# 第019步：播放端自适应缓冲

在现有Player内增加解码后缓冲控制。Publisher的ABR、编码前300ms/100ms队列裁剪与编码参数不变；本步不开展限带宽、RTT/丢包等综合实验。

## 对象和线程

- `SessionController`仍拥有`MediaPlayer`，GUI调用begin/stop/takeVideo，最多5Hz显示统计。
- `MediaPlayer::run`独占解码器，拥有一个`WasapiPlayback`输出线程；视频为独立GPU纹理，音频为48kHz立体声Float32 PCM。
- `PlaybackBuffer`是普通策略对象，不创建线程或访问设备。有声播放由WasapiPlayback在队列锁内使用：解码push记录交付，输出run采样并执行；关闭声音时由MediaPlayer在视频锁内使用同一策略，GUI取帧驱动消费。
- 默认仅低延迟直播启用。`MediaPlayer::begin`与`WasapiPlayback::begin`末参数`adaptiveBuffer=false`可显式保留固定预算对照；点播及`lowLatency=false`走原流程。界面不增加高级参数控件。

## 目标和安全上限

| 参数 | 本步值 | 含义 |
| --- | --- | --- |
| 初始/最低目标 | 50ms | 首播和重新缓冲的应用媒体准备量 |
| 最大目标 | 150ms | 抵抗交付波动的最高恢复门槛 |
| PCM固定安全上限 | 300ms | 防止持续积压；不会随目标无限扩大 |
| 设备待播上限 | 30ms | 仍读取实际容量，限制填入端点的数据 |
| 视频安全边界 | 500ms队头/新帧跨度及16张纹理 | 为音频重新缓冲和解码突发留空间；不是固定播放等待 |

启动/恢复以应用队列达到目标为门槛，运行时以应用剩余量加设备padding观察供给。目标变化、容量上限、队列当前水位是不同概念，不把这些参数相加当作端到端延迟。

## Controller → begin → start → run

1. Controller按原流程begin。Player清目标/队列/首帧统计后start；解码线程open并启动音频线程，begin重新建立50ms策略与交付基线。
2. 解码线程push PCM到应用队列。策略对比相邻交付的单调时间间隔与PTS间隔，记录正向迟到峰值和10%当前＋90%历史平滑值。PTS跳变/倒序重新建基线，不把不同进程或设备墙钟直接相减。
3. 每至少500ms采样；交付迟到峰值达到40ms且当前低于目标时，提高目标，至少增加20ms、最多150ms，增长冷却1秒。提高目标会受控排空端点、进入重新缓冲并实际补足水位，不只修改统计数字。实际断粮进入重新缓冲同样增加20ms；一次长断流只记一次，不因每10ms唤醒不断增长。
4. 至少两次有效交付、有足量媒体、无20ms以上迟交付，连续健康5秒后每2秒最多降低10ms。无媒体或长采样空档不算稳定。该指标包含网络、解码和线程调度影响，不冒充纯网络抖动或RTT。
5. 首播等待首张视频转换完成和足量PCM。输出最多30ms给设备，再Start；不靠提交大量静音推进时钟。
6. 正常运行应用队列空时先让已有设备padding播放完。确实断粮后Stop并Reset，冻结音频主时钟；视频继续按该时钟调度，不能独自向前。新PCM不足新目标就等待，达到目标才重新预填/Start，按首个保留PTS重建媒体映射。
7. 运行中超目标持续500ms才触发追赶，每次间隔至少1秒。普通超量留60ms余量，目标刚降低时留20ms余量，避免每次AAC批量交付都裁剪。先排空旧padding，再Stop/Reset，裁掉应用里尚未提交的PCM至当前目标，保留下一段PTS，恢复时做3ms淡入。
8. 300ms硬上限裁剪和媒体PTS缺口也由输出线程在旧padding排空后重映射，避免旧声音仍在设备中时先跳视频时钟。仅操作解码PCM/纹理，不任意丢弃压缩参考包。
9. 无音频输出时，Player先积攒视频至目标，再以首张PTS锚定QPC；最后一张视频到期且队列空时冻结时钟并提高恢复目标，恢复重新锚定；持续积压则裁已解码纹理、推进时钟。独立视频结束点避免被忽略的音轨拖着走。
10. stop关闭入口、中断读包/唤醒等待；即使正在预缓冲也及时退出。自然EOF不足目标仍排空已有媒体。设备与COM只在原输出线程归还，Player等待该线程后finished，下一轮重新begin，不继承旧目标或计数。

## 可观测和边界

现有状态标签增加目标、等待恢复/播放中、交付波动、目标升降次数和重新缓冲次数/已完成等待时长。重新缓冲统计包括断粮和策略主动提高目标后的补水位，启动不计入。保留PCM实际提交、主动丢弃、端点进度与应用补零计数；自适应欠载计数仅表示实际断粮暂停，固定模式仍保留原补零计数语义。

本步使用停止后恢复及分段丢弃追赶，没有接入保音高时间拉伸，不称为无感变速。3ms淡入仅减轻恢复边沿，不保证没有可感知跳跃；旧padding排空仍受音频引擎/驱动影响，不等同于扬声器声学测量。交付持续不足不能靠无限扩大缓冲解决，网络IO超时和已有错误退出仍有效。长期时钟漂移与源时间戳连续性问题另行处理。

仅扩展现有PlaybackTests和SRS集成，不增加测试程序。默认七组回归包含人工时钟策略：上下限、快速增大/慢减、冷却、空闲、实际追赶请求、重启及PTS跳变。`--adaptive-buffer`使用合成PCM和音量0的真实WASAPI，检查不足目标等待、欠载后时钟冻结、补足恢复、突发硬上限、真实PCM输出、不用补零假装播放、等待期间stop、重启以及不足目标的EOF排空。

正常SRS集成同时核对有声和关闭声音的GPU播放、目标边界、PCM/设备上限、帧交付与重复启停。其中合成视频源停顿200ms、音轨继续，验证关闭声音的Player真正冻结视频时钟、提高目标并恢复；不注入网络限速或丢包。既有`--latency`编号测量显式关闭自适应，保持第018步固定预算比较语义；本步不重新开展延迟或综合弱网实验，性能结论留待共同验收。
