# 需求与待定事项

状态：2026-10-06 启动初稿。明确需求与暂定实现方式分别记录。

## 用户明确提出的需求

1. 基于 CourseStudio 二次开发，提取关键技术栈。
2. 重构代码，简化复杂的 Qt 界面。
3. 按步骤重新设计网络、音视频采集、FFmpeg 编解码等模块的封装。
4. 补齐美颜的 GPU 链路。
5. 补充 AI 部署。
6. 补充 AI Agent。
7. 创建新文件夹，作为后续工作的起点。
8. 在同一个工程内分步骤推进，不需要编写多个独立 Demo；使用 Git 管理代码与阶段成果。
9. 不增加云助教相关功能，优先实现网络与登录。
10. UI 采用简单 MVC 架构。
11. 每做一个类画一张 UML 类图，每完成一个流程画一张 UML 时序图。
12. 首期登录重新设计 HTTP 接口，不沿用 yzj 的 TCP 登录协议。

## 已确认的推进方式

- 以 `CourseStudioNext` 作为持续演进的单一工程。
- 每次完成一个范围明确的小步骤，并在该工程内运行验证。
- 每个完成的小步骤用 Git 提交记录，保留需求、设计与验证依据。
- 已有 Demo 作为技术参考；新增能力逐步接入同一应用。

## 暂定工程原则

- 从最小可运行链路开始，每一步先确定职责、输入输出、生命周期，再写封装并验证。
- 模块需要明确资源所有权、线程归属、错误返回和停止流程。
- 媒体帧与音频数据需要明确格式、时间戳单位、时基和缓冲区有效期。
- 实时链路采用有界缓冲，分别定义预览、录制、推流及 AI 消费者的积压处理策略。
- Qt 界面负责交互和状态显示；采集、编解码、推理与 Agent 工具调用通过应用层连接。
- 优先利用已有 Demo 的经验，逐项核对其代码、运行结果和与主工程的差异。
- GPU 美颜的结果需要进入实际输出链路；减少不必要的 CPU/GPU 数据往返，并以测量结果判断优化收益。

以上是启动建议，并非用户已经指定的完整架构。

## 当前最不确定的事项

### 1. AI 部署与 Agent 的业务目标

“AI 部署”可能涉及本地视觉/语音模型、独立大模型服务，或同时包含两者。
Agent 的后续用途围绕媒体操作等实际能力收敛；云助教、课程转写、总结和教学问答不纳入当前范围。
需要先确定一个可演示的任务，才能确定模型输入、输出、工具接口和执行环境。

已有 `AIDataBridge` 可作为音视频采样与传输的参考，不能把它等同于完整推理部署或 Agent。

### 2. 产品边界与网络范围

已明确采用单工程逐步推进的方式。UI 提供点播/直播模式切换：点播支持本地文件及服务端列表在线播放；直播支持主播推流和观众拉流。
首期网络与登录使用新的 HTTP JSON 接口，已有客户端 MVC 和本地开发 root / root 登录。服务端将在 Linux OBS 容器内独立实现，先构建共用 Reactor 网络库，再迁移登录服务。
自建调度服务只返回合适的登录节点地址；自建信令使用 TCP 长连接、长度头、JSON，实现身份校验、直播间管理、开播停播、媒体地址、心跳及断线清理。FFmpeg 库用于客户端推拉流；媒体服务后续部署现成实现，不自行编写 RTMP 分发服务器。课程和云助教业务不纳入当前范围。
HTTP 业务通信与媒体推流应分别定义范围和验收目标。

### 3. 平台、硬件与性能要求

目前参考代码主要使用 Windows API 与 D3D11，可暂以 Windows 为分析起点。
客户端当前为 Windows Qt，服务端已确定为 Linux Docker，挂载本地 OBS server 目录。目标显卡/显存、分辨率、帧率、延迟预算及美颜质量尚未确定。
这些条件会影响推理后端、GPU 资源互通和软硬编解码选择。

### 4. 工程化选择

当前 CSN 使用 CMake、C++17、Qt 6 Widgets/Network；实际本机 Kit 为 Qt 6.11.2 + MSVC 2022。旧模块的复用比例按实际步骤判断。

## 阶段成果的基本要求

每个实际实现步骤记录：对应旧代码、封装职责、本工程内的使用方式、构建运行方法、验证结果及已知限制，并形成可回溯的 Git 提交。
每个手写 C++ 类提供类图，每个完成的流程提供时序图；图与实现同步维护。
性能数值必须来自实际运行，未验证的能力保持待验证状态。
