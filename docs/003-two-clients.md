# 第 003 步：推流端与播放端工作台

## 本步结果

一个 CMake 工程、两个入口：OBS_Publisher（推流端）和 OBS_Player（播放端）。源码继续平铺在 OBS client，不复制登录或网络代码。

本步完成双端工作台和真实服务器的控制流程：调度、HTTP 登录、TCP 认证、心跳、房间创建/分页列表/加入/退出、主播关闭通知、观众人数更新、断线重连及到期退出。摄像头、麦克风、FFmpeg、GPU 和实际媒体传输尚未接入。

播放端提供直播/点播切换，本地点播可以选择文件，在线点播可以输入地址；播放按钮保持禁用。推流端显示采集预览区域与后续链路说明，当前创建房间不会发送 live.start，也不会连接尚未部署的媒体服务。

## 打开和运行

1. 启动 OBS Docker，在远程终端运行：
   ```bash
   python3 /workspace/code/run_services.py start
   ```
2. Qt Creator 打开 OBS client/CMakeLists.txt，选择本机 Qt 6 / MSVC 64 位 Kit，重新配置并构建。
3. 在“项目 → 运行”分别选择 OBS_Publisher 与 OBS_Player；可启动两次，让两个程序同时运行。
4. 两端均输入开发账号 root、密码 root。默认调度地址为 http://127.0.0.1:8080/login/server，信令为 127.0.0.1:9000；密码不预填、不保存。
5. 推流端创建房间；播放端刷新列表、选择房间并加入。此时状态为“尚未开播”。
6. 观众退出、切换点播、主播关闭房间或退出登录，分别验证状态更新。

若服务器在另一台机器上，登录页修改调度与信令地址，同时修改服务端返回的 publicUrl 和媒体地址。当前默认仅面向本地 Docker 联调。

Windows 命令行构建和部署 Qt DLL：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build_clients.ps1 -LiveTests -Deploy
```

该命令只对本次脚本执行设置策略，自动查找 MSVC，使用默认 Qt 路径。其他安装位置使用 -QtRoot 参数。生成两个程序位于 OBS client/build-agent，可直接运行；Debug 依赖按本机开发环境部署，并非正式发布包。

## MVC 和对象关系

| 部分 | 类 / 文件 | 职责 |
| --- | --- | --- |
| 入口 | main.cpp、ClientRole.h | 两个 CMake 目标设置角色；装配相同模块 |
| View | MainWindow | 登录表单、角色工作台、模式切换；仅收集输入与显示状态 |
| 登录 Model | LoginModel | 登录状态、内存 token、用户和到期时间 |
| 登录 Controller | LoginController | 调度 GET、校验 loginUrl、登录 POST、取消和退出 |
| 工作台 Model | SessionModel | 信令状态、当前房间、列表快照、操作状态 |
| 工作台 Controller | SessionController | 角色校验、房间操作、分页、事件、登录到期和重连 |
| HTTP | HttpClient | 共用 GET/POST 生命周期、独立超时、取消和限长 |
| TCP | SignalClient | 帧收发、编号关联、认证、心跳、请求期限及缓冲限制 |
| 测试支持 | LocalAuthServer | 仅编译进原登录测试，不再随业务程序启动 |

Controller 借用 View/Model/网络类，不拥有这些对象。main.cpp 的声明顺序确保 Controller 先销毁。所有网络 API 在 Qt 事件循环中异步执行，无阻塞 GUI 的等待。媒体工作线程在后续采集阶段设计。

## 关键契约

- 调度只接收 GET，不接收账号密码。直接填写 /auth/login 时跳过调度。
- 调度成功后验证 HTTP(S) 地址和 userInfo/fragment，HTTPS 调度禁止降级到 HTTP 登录；不自动跟随 HTTP 重定向。
- 调度期间暂存凭据；进入 POST、取消或失败时立即解除暂存，UI 密码框点击登录后清空。会话仅驻留内存，不写配置和日志。
- 信令使用四字节大端长度加 UTF-8 JSON，单帧最多 64 KiB。按字符串 id 区分请求，分片与粘包逐帧处理；事件单独分发。
- 每次 TCP 连接使用新的 socket。连接、认证和各请求分别限制 5 秒，未完成请求最多 32，写队列最多 256 KiB。默认服务器下每 15 秒心跳。
- 业务请求超时意味着执行结果未知，因此关闭连接，让服务器清理房间，不继续沿用可能失配的状态。
- 每个客户端同时只执行一个房间操作；列表逐页汇总（每页由服务器控制），校验分页推进并限制总数 128。
- 连接断开、退出或登录到期，停止心跳和定时器并清空房间与列表。重连只重新认证，不自动恢复房间。
- 成员加入、离开或断开时，服务器向现有成员广播 room.updated；直播状态使用 live.changed；主播离开使用 room.closed。未加入的房间列表需手动刷新。
- 点播切换时若已加入直播房间，先发出退出请求；等待房间请求时禁用切换。失败保留实际房间状态，用户可退出或重连。
- 服务器可能先广播事件再返回响应；客户端不会用迟到的加入响应恢复已关闭房间。
- 目前保留 root 开发账号、无持久账号库、无中心令牌撤销；TLS/HTTPS 和生产认证属于部署阶段。

## 实际验证

本机 Qt 6.11.2 / MSVC x64 Debug 编译两个入口及测试目标成功。客户端三个 CTest 组通过：原登录 7 组行为、新增信令/调度/工作台 4 组行为、Docker 真实服务双端集成 1 组。

覆盖：HTTP 调度和直接登录、无效节点地址及调度取消；信令分片、粘包、编号关联、事件、心跳、非法帧、请求超时与重连；错误密码、房间创建、列表选择、加入、人数同步、点播切换退出、主播关闭/断线/窗口关闭清理、内存凭据清除与登录到期。

另验证列表分页汇总、无效分页关闭连接和关闭事件先于加入响应时不恢复房间。服务端 Debug 与 ASan/UBSan 各四个 CTest 组通过，并新增观众加入/离开通知断言。两个已部署 Qt 依赖的程序在移除 SDK PATH 后独立启动成功。截图生成到 out/推流端页面.png、out/播放端直播页面.png、out/播放端点播页面.png，均使用中文名且不进入源码仓库。

每个新增/修改类和流程均维护 Mermaid、中文 PNG 与 SVG，见 [UML 索引](uml.md)。
