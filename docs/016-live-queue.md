# 第016步：直播队列时效与积压恢复

本步实现编码前原始媒体队列的时效控制，接续[第015步](015-publish-control.md)的统计和运行时码率入口。只作用于直播；本地MP4继续原有数量上限、缺口补静音和尾部封存。自动码率、自动重连与新的RTMP缓冲调优仍是后续增量。

## 对象、线程与资源

`SessionController`在GUI持有录制/直播两个`MediaPublisher`。`pushVideo/pushAudio/stats/stop`只短暂加队列锁；`run`独占普通`MediaEncoder`、GPU帧池、AAC FIFO、封装与网络资源。本步不增加工作线程或MVC，不操作已编码参考包或已交给TCP的字节。

## Controller → begin → start → run

1. Controller沿用原入口传入`RecordingSettings`。`liveQueueLimitMs=300`、`liveQueueTargetMs=100`是初版高/低水位；只在C++设置中配置，界面暂不增加选项。这是本级队列预算，不是端到端延迟保证。
2. `begin`验证直播预算（`10 <= target < limit <= 5000`），清队列、统计、截止点和待交付追赶标记，再调用QThread的`start`。非法预算返回false，不启动线程。
3. `run`沿用首帧设备、RTMP握手、NVENC/AAC与FLV初始化。NVENC直播设置`forced-idr=1`，标记不连续的视频请求I帧时明确使用IDR。
4. GUI的媒体交付在入队时调用`trimLiveQueues`；工作线程在每次取帧前再检查一次。连接/写出曾阻塞且没有新输入时，出队检查仍能剔除已经过期的数据。清空后等待新媒体，不空转，不强留最后一张旧图。

## 高低水位与共同截止点

同时检查两项：队头入队后的单调时钟等待、队尾结束PTS到队头PTS的媒体跨度。跨度用于识别突发交付，年龄用于识别网络等待；不修改来源时间，也不把GPU处理完成时间当作采集时间。

任一项超过300ms时，按100ms窗口选取保留位置，同时排除等待已超过该目标窗口的队列前缀。截止点只前进；后续低于该点的迟到帧/包被拒绝。视频按整帧、音频按整10ms包处理，因此时间边界受帧/包粒度影响。

- 仅视频触发：推进视频截止点，优先保留连续声音。
- 音频也触发：推进音频截止点，并将同一截止点应用于视频；不能继续输出这段旧声音对应的旧画面。视频自己已经前进得更远时，不回退其截止点。
- 原16帧/50包硬上限仍保留，容量丢弃后的直播输入也通知编码器存在跳过。高水位和低水位降低反复贴线裁剪；它们不是网络带宽估计。

所有丢弃均发生在尚未编码的GPU纹理/PCM。出队时才把视频`discontinuity`或音频`liveCatchup`交给编码器，队列暂空时标记仍保留。录制与直播实例分别持有队列和标记。

## 音频追赶与时间戳

`MediaEncoder::pushAudio(packet, liveCatchup)`增加明确的主动追赶参数，默认false；不改通用`TimedAudioPacket`，也不把采集侧`discontinuity`一概当作主动丢弃。

普通包仍检查重叠并补有限静音；只有直播线程明确通知追赶时，丢弃未编码的FIFO残留，将`audioCursor/audioInputEnd`推进到下一包的原PTS，不补回主动跳过的整段时间。原PTS继续保留，视频不重新编号，音频时间也不压短。首次音频直接从首个被接受包建立游标。

AAC内部已经接受的帧及封装/网络中的包不会因为重置外部FIFO而消失；它们保持原时间戳。解码器已有PTS跳变时重建SWR的路径，直播WASAPI已有大缺口追赶路径。本步独立验证AAC编码/解码PTS与实际收到的FLV；不以清FIFO宣称整个链路已无缓存。

## 统计、停止与重启

新增过期视频/音频数量、队列裁剪次数、编码器音频追赶次数及跳过样本量。`droppedVideo/droppedAudio`保留总丢弃数，`expired*`是其中的时间策略子集；`skippedAudioSamples`包含编码时间缺口与FIFO残留，不当成新增补静音。

Controller沿用最多5Hz的诊断刷新。`publishStats`只合并编码器拥有的字段，保留GUI并发写入的目标与队列计数。`stop`关闭入口并取消直播IO，清理资源后`finished`回GUI才允许下一轮；`begin`会重置截止点和追赶标记，旧策略状态不进入新会话。

## 运行与验证

```powershell
./scripts/build_clients.ps1 -Deploy
python scripts/run_publish_checks.py
python scripts/run_publish_checks.py --gpu --weak-network
python scripts/run_checks.py
```

默认测试只使用WARP人工纹理、静音PCM与本机故意不回答的握手端点，覆盖高低水位、共同截止点、迟到拒绝、整批过期、纯音频、预算校验、停止/重启、普通音频缺口与主动追赶的区别。AAC专项将普通50ms缺口补2400样本静音，再主动跳到5秒：跳过234880样本（含FIFO）、只输出10个AAC包，独立解码10240样本且PTS跨越缺口，未补回数秒静音。

`--gpu`保留同一NVENC会话270帧、运行时3000→400→2000kbps及MP4独立重读验证。`--weak-network`启动临时FFmpeg RTMP收流进程和本机TCP代理，使用预生成噪声纹理/静音PCM，不打开实际采集源、不修改系统网络、不依赖业务服务器或SRS。

隔离测试先暂停握手超过队列预算且不再入队，放行后确认出队检查剔除旧媒体、未送入编码器；随后在正常推流中暂停代理读取，确实观察到媒体写出阻塞超过350ms后恢复。检查队列裁剪、音频主动跳过、码率入口仍可使用、同会话恢复与停止，再独立重读收到的FLV，核对两轨PTS、保留的时间缺口、D3D11 GPU解码与尾部时间差。

2026-10-16本机专项通过：代理暂停902ms，最长写出986.4ms；恢复后已编码帧10→59，过期丢弃视频51/音频168，执行4次音频追赶，跳过80864样本且补静音为0。收流文件独立GPU解码56帧，最大音频缺口1043.3ms，尾部音画时间差43.7ms，停止5ms。NVENC调码率实测仍为3299→431→2634kbps。以上是生成素材和本机受控阻塞的单次结果，不是互联网弱网或感知音画同步的通用保证。

完整10组CTest通过（20.89秒）。既有SRS链路两轮各GPU解码132帧、显示121帧，观众音频补静音0/1次；停止136/124ms，无响应推/拉握手取消78/79ms。Publisher MVC运行时调码率与本地美颜通过，53张美颜帧进入RTMP及GPU播放。测试结束已恢复业务服务和OBS-SRS停止，OBS开发容器继续运行。

640×480窗口和二倍缩放的码率输入、应用按钮及完整追赶统计均通过可滚动显示检查；截图在`out/队列恢复验证/`。中文时序图已生成SVG/PNG，不更新历史类图。

## 边界与后续

- 编码/GPU慢也会触发过期处理；本策略控制媒体时效，不据此单独认定网络拥塞。
- 预算检查发生在入队和出队时，未到检查点的队列可能已变旧；当前正在执行的编码/写出不可由清队列撤回。没有数据到达时无需额外启动清理线程，出队前重新检查即可。
- 已进入TCP的旧字节仍可能延迟恢复，持续带宽不足也不会仅靠丢原始帧得到解决；仍受现有5秒IO超时限制，自动重连尚未实现。
- 主动追赶会牺牲这段声音/画面，未加入音频交叉淡化，不能承诺无听感突变。
- 下一步才根据多项观测实现自动码率、迟滞/冷却与恢复探测，再分别调低延迟缓冲，开展限带宽、时延/丢包和长期运行验收。
