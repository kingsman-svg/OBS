# 第017步：直播自适应视频码率

在[第015步参数入口](015-publish-control.md)与[第016步时效队列](016-live-queue.md)上接入ABR。本步是应用层发送压力反馈策略，通过FFmpeg/NVENC改变视频目标；TCP的拥塞控制仍由系统完成，不宣称实现GCC、精确带宽估计或观众下行自适应。

后续状态：[第018步](018-rtmp-latency.md)已统一直播低延迟预算并增加编号画面对照测量；ABR调目标时保留新的VBV时间预算，下文保留第017步原始验收记录。

## 对象与线程

`SessionController`仍在GUI编排采集、同步、直播。`MediaPublisher::run`独占普通`AdaptiveBitrate`、`MediaEncoder`和封装/网络资源；新策略不持线程、锁或FFmpeg上下文。只新增`ffmpeg/AdaptiveBitrate.h/.cpp`，未新增测试程序或工作线程。

`BitrateControl`把模式、下限、上限作为完整配置；`BitrateFeedback`保存累计媒体/写出/处理/丢弃数据与本采样期写出峰值。策略用人工单调时间也能直接验证。

## Controller → begin → start → run

1. 界面默认手动。码率输入在手动模式是固定目标，在自动模式是上限；另有“自动码率”和最低码率（默认400kbps）。下限输入不能超过上限，开关/数字编辑均不立即发送；运行时点“应用设置”才原子提交。
2. Controller开播时读取选择，传入`RecordingSettings`；纯音频不启用视频ABR。`begin`验证自动模式仅用于直播视频、范围有效，清统计/邮箱/队列，再start。
3. 工作线程初始化编码和RTMP后，建立策略及累计反馈基线。GUI的`requestBitrateControl`只加短锁覆盖最新整份配置；旧`requestVideoBitrate`保留，明确等价于切回手动固定目标。
4. `run`取媒体前先裁剪过期队列、接收参数，再评估策略；自动模式无媒体时最多每100ms醒来形成空闲观察，手动/录制继续条件等待。
5. 策略计划值与上次提交值不同时，在下一张视频前调用原有`MediaEncoder::setVideoBitrate`，随后编码该帧。PTS、尺寸、GPU帧池与连接不因码率调整重建。

GUI不直接写编码上下文。网络写出阻塞时GUI仍可操作，但策略和参数的实际应用需要等该调用返回；现有5秒IO超时继续有效。

## 反馈与决策

每至少500ms取一次累计差值：媒体写出占用的墙钟时间、视频处理耗时、编码帧数、写出字节与过期丢弃。写出占时用当前30%＋历史70%的EWMA；最长写出仅保留自上次取样以来的值，取样后清零，避免一个历史峰值反复触发下降。

- 单次媒体写出达到250ms：作为严重发送压力，目标下降25%。
- 平滑写出占时≥65%，或占时≥30%同时新增过期/队头等待≥150ms：连续两个窗口确认后下降20%。
- 相邻自动下降至少间隔1.5秒；所有目标受下限约束，到底仍有压力时明确显示，不继续假装码率还能解决问题。
- 视频平均处理接近固定30fps预算（28ms）且写出压力低：显示处理瓶颈，不据队列积压单独判定网络拥塞。
- 无媒体、长观察空档或素材实际码率很低：不把空闲当作网络恢复；严重真实写阻塞仍保留下降证据。
- 平滑写出占时<55%、本窗口最长写出<100ms、队头等待<80ms、没有新增过期，窗口至少编码4帧且实际视频码率≥当前目标的一半：持续稳定5秒后才小步上探；每3秒至多一次，每次10%并限制在50～500kbps。达到上限停止上探。上下调阈值之间留出迟滞，任一不健康窗口会重新计算稳定时间。

实际压缩码率用于判断是否存在足够媒体负载；本机IO字节不被当成可用带宽，也没有用它减去音频后冒充精确视频预算。音频保持原码率，其写出压力已包含在总反馈中。

阈值包含本地链路校准：串行RTMP写出即使队列稳定仍可能占用较多墙钟时间，不能要求接近空闲才恢复。直播连接同时开启FFmpeg的`tcp_nodelay=1`以减少小包等待；这不等于完成端到端低延迟优化，也不保证消除写出阻塞。

## 模式与边界

切回手动立即计划用户指定目标，策略停止自动调整。进入自动模式保留当前目标并裁到新范围，不能仅因提高上限就立刻跳高；改变范围/模式清旧观测，避免把上一模式的拥塞或稳定时间直接套用到新设置。自动调整计数保留至本轮结束，`begin`才清零。

界面区分用户目标/上限、工作线程计划值、编码器提交值、真实视频包码率和本机IO码率，并展示待接收配置、策略原因、自动升降次数及平滑写出占时。计划与编码器目标不一致时仍提示等待下一视频提交。驱动是否实际完成重配置继续结合码流验证，不能只凭上下文字段宣称确认。

`stop`关入口、清未消费配置并取消直播IO；局部策略和编码器随run结束释放。Controller收到finished后才能重启，新一轮没有旧反馈/冷却/范围状态。本地MP4拒绝自动模式，保留原手动调参和文件安全收尾。

按本次用户要求先启动现有OBS、OBS-SRS和业务服务，并保持运行：SSH仍用127.0.0.1:2222，登录调度8080、登录节点8081/8082、信令9000、RTMP1935。不涉及Mac研究项目。

默认`client.publish_control`增加人工时钟策略验证：手动隔离、严重/持续压力下降、冷却、慢升、处理瓶颈、仅过期不降、低负载/空闲不升、上下限、切换/重启及50Mbps整数范围；另验证UI完整配置提交、下限随上限收敛与停止锁定。

现有隔离代理使用本机RTMP收流进程、预生成纹理和静音PCM，暂停应用读取制造真实写出背压，恢复后观察自动目标，再验证手动接管；原有实际FLV时间戳、AAC追赶和GPU解码检查继续执行。输出640×360，为编码处理留余量，避免本机处理饱和干扰网络恢复验收。代理不修改系统网络，保留系统TCP自动调节；素材需要具有可压缩性，不能以不可压缩强噪声的最低码率代替网络承载能力。

现有SRS集成继续验证两轮推拉流和美颜，增加实际Publisher按钮的手动/自动切换、上限修改后保留当前目标以及关闭房间清理。历史独立硬件/UI测试不恢复。

## 限制与下一步

阈值是本项目初版启发式，写出还包含封装/协议成本；RTMP缺少当前实现可用的接收端反馈，不能精确区分所有路径瓶颈或保证公平性、端到端延迟。CBR不是瞬时带宽硬上限，复杂画面、关键帧和硬件QP限制仍可能使实际输出超目标。

本步不改变分辨率、帧率，不增加自动重连、传输层算法或WebRTC。达到最低目标仍积压时继续依赖队列时效和超时，后续再根据实测增加降负载手段。下一步分别调优RTMP编码/发送/播放缓冲，并开展限带宽、时延/丢包和长时间运行验收。
