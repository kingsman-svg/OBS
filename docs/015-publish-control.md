# 第015步：推流观测与运行时手动码率

本步完成[弱网计划](weak-network.md)的统计和手动参数入口。发送队列仍采用原有数量上限；自适应算法、按帧龄丢弃、重连恢复和新的低延迟缓冲策略尚未接入。本步不新增工作线程、MVC或类图。

后续状态：第016步已增加[直播队列时效与积压恢复](016-live-queue.md)，第017步已增加[自动码率与模式切换](017-abr.md)。下面保留第015步当时的范围和验收记录，当前时序图随最新实现更新。

## 对象和线程

GUI的`SessionController`分别持有本地录制和直播的`MediaPublisher`。每个Publisher是一个QThread，`run`局部独占普通`MediaEncoder`及FFmpeg封装/网络IO资源。实时参数和原始媒体分别进入有界邮箱与队列；GUI不直接修改AVCodecContext，不等待编码/GPU/网络。

`RecordingSettings`保存本轮初始参数；新请求存到Publisher的`m_pendingVideoBitrate`单值邮箱，后来的请求覆盖未处理的旧请求。编码器自身参数只能由工作线程修改。

## Controller → begin → start → run

1. Publisher界面“视频目标码率”以kbps输入，默认4000，范围100～50000。开播时Controller读取并转成bit/s，随本轮设置传给`begin`。
2. `begin`清队列、输出窗口与各项统计，记录初始请求，随后`start`；构造/begin不访问NVENC或网络。
3. `run`等首帧设备，连接RTMP、建立NVENC/AAC和FLV，流程沿用现有实现。
4. 用户运行中点“应用码率”，View只发`liveVideoBitrateRequested`。修改数字本身不立即发送请求，避免逐字输入触发多次重配置。
5. Controller检查本轮状态，调用`requestVideoBitrate`；Publisher加短锁验证范围与视频入口，保存最新请求后立即返回。纯音频、停止后、未运行或非法目标会拒绝。纯音频/停止中的应用按钮禁用。
6. `run`取下一张视频时同时取走参数邮箱，解锁后调用`MediaEncoder.setVideoBitrate`，再提交视频。没有视频时仍保留待提交请求；网络写出阻塞时也需等工作线程返回，GUI不会被一起阻塞。

## 编码器动态目标与实际效果

只在当前编码线程设置公开的`AVCodecContext.bit_rate/rc_max_rate/rc_buffer_size`；尺寸、帧池、时间基和输入PTS保持原契约，相同目标不重复触发改变。FFmpeg7.1在下一次NVENC `send_frame`内发现变化，调用原生重配置并请求IDR。当前保留既有约2秒VBV量级，低延迟VBV调整留给下一步按实测验收。

界面明确区分：

| 数值 | 含义 |
| --- | --- |
| 请求码率 | 用户最新提交的目标 |
| 编码器目标 | 已随视频帧交给编码器的目标，未提交时保留等待提示 |
| 视频压缩码率 | 最近最多1秒媒体PTS内的视频包字节×8/媒体时长，不含音频/封装 |
| 本机发送码率 | 最近1秒墙钟内RTMP交给底层IO的媒体字节×8，含封装，不含连接/文件头 |

首次视频不足1秒时显示实际媒体窗口长度；本机发送窗口固定1秒，启动时可能偏低、空闲超过1秒自然归零。发送统计不等于TCP已确认字节、观众吞吐或可用带宽。重配置不要求每个1秒窗口的实际码率精确等于目标。

FFmpeg7.1的NVENC内部重配置部分错误仅记日志，未必从send_frame返回失败；因此界面只称“编码器目标”，不宣称驱动已确认。真正生效需要实际视频包统计/测试核对，不访问不稳定的NVENC私有结构。可见编码/IO错误仍沿用failed清理；非法请求不会覆盖旧目标。

## Publisher统计

- **队列**：视频/音频数量、峰值、PTS媒体跨度和队头入队后的墙钟等待。数量有界不代表数据新鲜，时间观测为下一步过期处理提供依据。
- **写出**：对媒体包的`av_interleaved_write_frame`及显式`avio_flush`整体计时，记录最近/最长/累计、次数与失败数。GUI读取时可观察当前尚未返回调用已等待多久。包含交织/IO成本，不当成网络RTT。
- **处理**：视频GPU绘制/编码调用墙钟耗时减掉其同步sink写出耗时；它包含本地处理开销，不是GPU event精确计时。
- **合并**：编码器统计逐项复制，保留GUI并发请求、入口丢弃、队列峰值及IO数据，避免整份覆盖导致统计或参数回退。

所有等待用单调时钟。媒体PTS窗口与墙钟发送窗口分别管理，不把快速离线录制速度当作视频播放码率。工作台诊断文本最多5Hz更新，启停/错误/手动请求事件立即刷新，媒体交付仍按原频率进行。统计不输出媒体URL或认证信息。

## stop → finished → 重启

`stop`撤销入口并清尚未消费的参数，直播中断网络IO；本地MP4仍排空尾部封存。`abort`丢队列和请求。当前已取出的帧属于正在执行的工作，不能通过GUI修改其上下文。资源归还后发结果/finished，Controller再开放下一轮；`begin`重置参数与统计，旧请求不会进入新会话。

## 运行与验证

```powershell
./scripts/build_clients.ps1 -Deploy
python scripts/run_publish_checks.py
python scripts/run_publish_checks.py --gpu
```

先启动既有登录/信令及Windows媒体服务。Publisher创建房间、选择视频源，设置初始码率后开播；运行中输入新值并点“应用码率”，观察请求、编码目标、视频包码率及队列/写出统计。本地录制仍使用另一输出实例，本界面只调直播实例。

默认`client.publish_control`只用WARP人工纹理、静音PCM和本机不回答RTMP握手的测试端点，验证数量/跨度/等待/峰值、合并请求、IO阻塞期间GUI响应、停止拒绝/重启清零、纯音频与文件写出统计、明确应用按钮与小窗口；不打开有效采集源，不依赖外部容器。

`--gpu`显式验证RTX/NVENC，生成270张640×360限幅噪声帧，在同一会话中调3000→400→2000kbps。每段3秒，独立重新解封装MP4核对各段末秒包字节、连续PTS/DTS、请求后的关键帧以及只有一次opened。临时文件测试后清理。

`python SRS/check.py`继续验证现有Windows RTMP：两轮运行中降码率/回升、实际Publisher初始值和应用按钮、观众GPU解码、输出统计和关闭房间。测试只采集自建窗口；不涉及Mac三个研究项目。

## 实测与限制

本机2026-10-16、RTX5060、FFmpeg7.1/Qt6.11.2构建及10组CTest通过。显式NVENC专项270帧、连续9秒媒体，只打开一次编码器；3000→400→2000kbps目标对应末秒窗口约3299→431→2634kbps，独立重读文件确认包字节完全一致、PTS/DTS连续、调整后出现关键帧，无输入丢帧。目标与实际输出并不精确相等。

RTMP两轮均通过500→1200kbps运行中调整，观众各解码132张GPU帧；本机输出窗口约413kbps（素材主要为静止画面与合成声音），最长媒体写出分别0.46/0.24ms，队列峰值视频5/5、音频18/17。播放端两轮分别跳过4/0张过期画面、补静音0/1次，作为后续优化基线保留，未宣称零卡顿。真实Publisher初始800kbps、点击应用600kbps通过，模型美颜与观众GPU播放回归通过。正常停止129～146ms，故意不回答的握手取消95～97ms；测试后恢复业务服务及OBS-SRS原停止状态。这些是同机短测，不是互联网弱网/端到端延迟保证。

WARP人工队列验证16帧/50包、533/500ms媒体跨度及等待时间，握手阻塞期间100次参数/统计调用快速返回，停止拒绝请求、两轮重置和纯音频拒绝调视频均通过。640×480小窗口及二倍缩放控件完整可见，截图在`out/推流控制验证/`。

初次全幅强噪声试验中，400kbps目标仍产生约1.3Mbps视频，暴露内容复杂度/量化上限与码率峰值限制；不能据目标下降宣称已解决拥塞。自适应必须继续观察实际输出和积压，按策略决定能否继续降码率或需要其他降负载手段。

本步未承诺端到端延迟、弱网自适应效果或自动重连。跨机延迟、隔离限带宽/丢包、队列按时间淘汰和自适应控制继续按计划增量实现。
